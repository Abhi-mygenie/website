# CR-260 — Calendly Webhook Self-Recovery & Missed-Booking Backfill

**Status:** Open  
**Priority:** P0 — Production revenue impact (every missed booking = lost demo = lost deal)  
**Raised:** 2026-11-25  
**Subsumes:** CR-40 (gap), CR-59 (gap)  
**Files affected:** `backend/server.py`, `backend/scripts/register_calendly_webhook.py` (new script needed)

---

## Background

CR-40 added auto-registration of the Calendly webhook on backend startup.  
CR-59 added an allow-list so preview environments can't hijack the production subscription.

Both are in `_sync_calendly_webhook()` in `server.py`.

Neither CR handled the **disabled** state — a state Calendly puts a subscription into after 24 hours of failed deliveries. This gap means the system cannot self-recover once a subscription is disabled, and the problem repeats on every deploy.

---

## What Is Actually Happening (Root Cause Chain)

```
1. Subscription is working fine
        ↓
2. Backend returns 400 or 401 to Calendly on a webhook delivery
   (see Bug B below for why this happens)
        ↓
3. Calendly retries for 24 hours — all fail
        ↓
4. Calendly sets subscription state → "disabled"
        ↓
5. Backend restarts (deploy, pod recycle, etc.)
        ↓
6. _sync_calendly_webhook() runs
   - Step 3: checks state == "active" → disabled sub doesn't match → continues
   - Step 4: deletes only "active" subs → disabled sub NOT deleted   ← Bug A
   - Step 5: POST new subscription → Calendly returns 409 Conflict
             ("subscription for this URL already exists, even if disabled")
        ↓
7. WARNING logged, nothing fixed. Subscription stays disabled forever.
        ↓
8. Next deploy → same cycle. Repeat indefinitely.
```

---

## Three Bugs to Fix

### Bug A — Disabled subscriptions are never cleaned up  (PRIMARY)

**Location:** `server.py` line 1678  
**Current code:**
```python
for s in subs:
    if s.get("state") == "active":          # ← only deletes active
        sub_id = s["uri"].split("/")[-1]
        await client.delete(...)
```
**Problem:** A `disabled` subscription blocks any new POST for the same URL with 409.  
The disabled sub is never deleted, so re-registration fails on every restart forever.  
**Fix required:** Also delete subscriptions with `state == "disabled"`.

---

### Bug B — Step 3 early-return ignores signing key mismatch  (TRIGGER)

**Location:** `server.py` lines 1669–1675  
**Current code:**
```python
if any(
    s.get("callback_url", "").rstrip("/") == callback_url
    and s.get("state") == "active"
    for s in subs
):
    return  # nothing to do
```
**Problem:** Returns early if URL matches and state is active — even if the subscription  
was created with a *different* signing key (or no signing key at all, e.g. manually created  
before CR-40). Calendly keeps sending webhooks using the old signing key. The server  
verifies with the new env var value → mismatch → 400/401 → Calendly disables after 24h.  
**Fix required:** Also check that the subscription's signing key matches the current env var.  
If it doesn't, delete and recreate the subscription (Calendly has no PATCH/update endpoint).

---

### Bug C — `CALENDLY_WEBHOOK_SIGNING_KEY` loaded at module level, not at request time  (COMPOUNDING)

**Location:** `server.py` line 482  
**Current code:**
```python
CALENDLY_WEBHOOK_SIGNING_KEY = os.environ.get("CALENDLY_WEBHOOK_SIGNING_KEY")  # module-level
```
**Problem:** This variable is frozen at module import time. If the env var is updated  
between restarts (secrets updated via platform UI without full restart), the verification  
function (`_verify_calendly_signature`) uses a stale value. The registration function  
at line 1630 reads `os.environ.get()` fresh each call — so there's an inconsistency:  
registration uses the NEW key, verification uses the OLD key → signature mismatch → 400.  
**Fix required:** Read `os.environ.get("CALENDLY_WEBHOOK_SIGNING_KEY")` inside  
`_verify_calendly_signature()` at call time, not at module level.

## Missing Data Recovery (Backfill Script — to be built as part of this CR)

When the subscription was disabled, every Calendly booking silently missed two things:

1. `db.demo_requests` record was NOT updated → `status` stays at pre-booking state, no `demo_at` / `meet_link`
2. `freshsales.mark_demo_booked()` was NOT called → Freshsales contact stage not moved to "Demo Booked"

**New script:** `backend/scripts/cr260_backfill_calendly.py`

Logic:
```
1. Call GET https://api.calendly.com/scheduled_events
       ?user=<user_uri>&min_start_time=<from>&max_start_time=<to>
2. For each event, fetch invitees: GET /scheduled_events/{uuid}/invitees
3. For each invitee, check if db.demo_requests already has status=demo_booked
       → skip if already processed
4. If not processed → call the same logic as /api/calendly/webhook handler:
       - update db.demo_requests
       - call freshsales.mark_demo_booked()
5. Log each action to db.cr260_backfill_log for audit
```

**Usage:**
```bash
python scripts/cr260_backfill_calendly.py --from 2026-10-01 --to 2026-11-25 --dry-run
python scripts/cr260_backfill_calendly.py --from 2026-10-01 --to 2026-11-25
```

## Implementation Notes

- Calendly has no PATCH/update endpoint for webhook subscriptions — delete + recreate is the only way to change signing key
- The signing key is Calendly's secret for verifying delivery — it must match between what was registered and what the server uses to verify
- Calendly disables after 24h of failed deliveries with no manual re-enable option — the subscription must be deleted and recreated
- `_sync_calendly_webhook` is `best-effort` (never raises) — keep that contract, all new logic must be inside the existing try/except
- CR-59 allow-list (`CALENDLY_WEBHOOK_ALLOWED_HOSTS`) must remain intact — no preview environment should ever touch the production subscription
